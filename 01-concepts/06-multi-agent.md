# 06 · 多 Agent 协作

## 什么时候需要多个 Agent？

单 Agent 能搞定大多数任务。考虑多 Agent 当：

- 角色冲突明显（写代码的人不宜同时当最终审查者）  
- 任务可并行（调研 A / 调研 B 同时进行）  
- 需要辩论或交叉验证提高质量  
- 系统提示已经膨胀到「一个提示里塞不下多种人格」  

代价：更贵、更慢、更难调试。**能单则单。**

## 常见拓扑

### 1. 流水线（Pipeline）

```
研究员 → 写手 → 编辑
```

上一环输出是下一环输入。简单、可控。

### 2. 主管 + 工人（Supervisor / Router）

```
        ┌→ 代码 Agent
主管 ───┼→ 文档 Agent
        └→ 测试 Agent
```

主管负责任务分发与汇总。类似项目经理。

### 3. 辩论 / 评审（Debate / Review）

```
提案 Agent ↔ 批评 Agent → 综合
```

适合方案选型、安全审查。

### 4. 群聊（Group Chat）

多个角色轮流发言，由选择器决定下一个说话的人。灵活但容易跑题，需要强约束。

## 共享什么？

多 Agent 系统要明确共享状态：

| 共享内容 | 说明 |
|----------|------|
| 目标与约束 | 大家为同一结果服务 |
| 黑板 / 状态对象 | 已收集事实、待办、产物路径 |
| 工具权限 | 谁能写文件、谁只能读 |
| 消息协议 | JSON schema，避免纯散文传递 |

## 设计清单

1. 每个 Agent **一个清晰角色**（Single Responsibility）  
2. 输入输出格式固定（方便下一环）  
3. 设最大回合数，防止互相抬杠到死  
4. 关键写操作仍由**一个**角色或人工把关  
5. 先画拓扑图，再写提示词  
6. **按角色拆、按项目组装**——不要「一项目一只大杂烩 Agent」  

## 和「工作流」的边界

- **多 Agent**：角色用自然语言分工，路由较灵活  
- **工作流 / Graph**：节点与边写死，LLM 只在节点内决策  

可控性要求高（金融、客服 SOP）→ 偏工作流。  
探索性强（研究、头脑风暴）→ 偏多 Agent。

## 下一步（拆分节奏）

多 Agent 里的「人」，应沉淀成可复用**角色卡**，再被不同**项目**请来上场。
