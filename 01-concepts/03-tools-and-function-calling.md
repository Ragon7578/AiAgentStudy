# 03 · 工具与函数调用

## 为什么必须有工具

没有工具的 LLM：只能根据训练知识「说」。  
有工具的 Agent：可以「做」——查、算、读、写、调 API。

工具是 Agent 的手和脚。

## 工具的三要素

定义一个工具，通常需要：

1. **名字**：`get_weather`  
2. **描述**：给模型看的自然语言说明（写清楚「何时用」）  
3. **参数 Schema**：类型、必填项、枚举值  

示例（概念）：

```python
{
  "name": "search_web",
  "description": "搜索互联网获取最新信息。当问题涉及实时新闻、价格、版本号时使用。",
  "parameters": {
    "type": "object",
    "properties": {
      "query": {"type": "string", "description": "搜索关键词"}
    },
    "required": ["query"]
  }
}
```

描述写得好，模型才知道**什么时候该调、怎么填参数**。

## 调用闭环

```
用户: 上海今天适合户外运动吗？
        │
        ▼
模型决定: 调用 get_weather(city="上海")
        │
        ▼
框架执行函数 → 返回 {"temp": 28, "rain": 0.8, ...}
        │
        ▼
模型根据结果回答: 降水概率高，不太适合……
```

关键点：**执行发生在框架侧**，模型只产出「意图」。

## 常见工具类型

| 类型 | 例子 | 注意 |
|------|------|------|
| 只读信息 | 天气、搜索、查库 | 风险低，适合入门 |
| 计算 | 计算器、代码执行器 | 防死循环 / 超时 |
| 文件 | 读 README、写报告 | 限制目录范围 |
| 终端 | `git status`、跑测试 | 沙箱 + 命令白名单 |
| 写操作 | 发邮件、改库、下单 | **必须人工确认** |

## 设计原则（很实用）

1. **少而精**：工具太多，模型容易选错  
2. **描述要含边界**：说明「不要用于……」  
3. **参数尽量简单**：嵌套过深容易填错  
4. **返回值结构化**：JSON 优于大段散文  
5. **失败可恢复**：返回明确错误，让模型换策略  
6. **危险操作二次确认**：尤其是删除、支付、推送  

## 与 RAG 的区别（常被混淆）

| | RAG | Tools |
|---|---|---|
| 时机 | 回答前检索知识 | 决策中途按需调用 |
| 典型用途 | 私有文档问答 | 查实时数据、执行动作 |
| 关系 | 检索也可做成一种工具 | Agent 可同时用 RAG + 其他工具 |

实践中常把「向量检索」注册成 `search_docs` 工具，由 Agent 自己决定何时检索。
